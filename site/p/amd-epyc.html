xoa, 2022-05-28 in “OpenBSD 7.1”

I bet AMD itself is not able to get even close to the 204 GB/s bandwidth that they "promise" for these CPUs. AMD instructions for measuring peak bandwidth are here: https://developer.amd.com/spack/stream-benchmark/ (essentially does a multi threaded memcpy). The script there will pin 1 thread per CCD, and with 8 threads you'll get close to peak bandwidth on CPUs with 8 CCDs (adding more threads doesn't help). I've run it in the same CPUs that AMD uses there, following their instructions to the letter, which should be able to achieve 204 GB/s, but the best I've seen is about 165 GB/s. That's 80% of what AMD advertises. HOWEVER, THIS NUMBER IS A LIE. It is using the AMD compiler with a flag called "-fnt-store" to turn all stores into non-temporal stores. This is something that no real-world application in practice would actually do because it does not make sense doing in general. Without this flag, the peak bandwidth that AMD scripts report is about 124 GB/s. That's 60% of what AMD advertises and the best that most applications can aim to obtain in practice (the blog post author is really close to it). The fine print ( https://www.amd.com/en/products/cpu/amd-epyc-7742 ) does say that 204 GB/s is a "theoretical" number. So I bought a "theoretical" 204 GB/s CPU that delivers 60% of what it "theoretically" promised. I feel scammed. --- Instead, if I run STREAM on my GPU, I get close to 100% of what the GPU promises, and about 90% or so of it in practice.
